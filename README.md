# MiniMaxBrain

> **Run Mixture-of-Experts models by paging expert weights from SSD instead of keeping the entire expert bank resident in RAM.**

MiniMaxBrain (MMB) is an experimental **MoE inference runtime** integrated directly with `llama.cpp` / GGML.

It preserves the model's real router and existing GGML kernels, but changes **where routed expert weights live**. Experts stay in `.mmbw` storage and are brought into a bounded RAM cache only when the model actually selects them.

MMB is **not a compression format** and does not reduce the logical parameter count of the model. It is a residency and paging architecture.

---

## Why MiniMaxBrain?

Mixture-of-Experts models can contain a very large expert bank while activating only a small subset of experts for each token.

Conventional loading strategies may require a large portion of those weights to remain resident or mapped as part of the model runtime.

MMB separates:

```text
logical model size
        │
        ├── core working set ───────────────► resident
        │
        └── routed expert bank ─────────────► MMBW / SSD
                                                │
                                      router selects experts
                                                │
                                                ▼
                                         bounded RAM cache
```

The goal is simple:

> **RAM usage should follow the active working set, not the total size of the expert bank.**

## Real-model validation

MMB has been validated on a real `qwen35moe` model with:

```text
40 layers
256 routed experts
top-8 active experts
10.86 GiB GGUF reference
1 GiB expert-cache budget
CPU / AVX2
```

The acceptance run produced:

```text
token_parity=true
paged_kernel_used=true
paged_kernel_invocations=840
router_requests=840
cache_hits=7948
cache_misses=2231
bytes_read=2275975168
peak_resident_bytes=1073741824
mmb_source=metadata+core_mmbw+expert_mmbw
```

The greedy token sequence generated by the MMB path was identical to the GGUF baseline for the acceptance case.

This proves that, in that tested configuration:

- the **real model router** selected the experts;
- expert bytes came from **MMBW**;
- those bytes reached the existing GGML `MUL_MAT_ID` kernel;
- leases kept the expert memory valid until compute completed;
- the expert cache respected its **1 GiB** budget;
- the tested greedy output matched the baseline.

> The 1 GiB number is the **expert cache budget**, not total process RAM. Core weights, KV state, compute buffers and runtime overhead use additional memory.

See [`REAL_TESTS.md`](REAL_TESTS.md) for the validation protocol.

## Architecture

```text
Chat / Web / API
      │
      ▼
MMBRuntime
      │
      ▼
mmb_backend
      │
      ▼
MMBLlamaRuntime
      │
      ├── metadata-only GGUF
      └── core weights from MMBW
      │
      ▼
llama.cpp graph
      │
      ▼
real MoE router
      │
      ▼
GGML_OP_MUL_MAT_ID
      │
      ▼
MMB MoE provider
      │
      ▼
MMBKernelLease
      │
      ▼
MMBPager / MMBCache
      │
      ▼
expert block from .mmbw
      │
      ▼
existing GGML kernel
```

MMB deliberately intercepts only supported routed expert weights:

```text
blk.*.ffn_down_exps.weight
blk.*.ffn_gate_exps.weight
blk.*.ffn_up_exps.weight
```

The rest of the model follows the normal llama.cpp / GGML execution path.

More detail: [`docs/runtime-architecture.md`](docs/runtime-architecture.md)

## MMB bundle

A converted bundle contains:

```text
model-mmbw/
├── gate.json
├── model.mmb-map.json
├── model.mmb-layout.json
├── model.mmb-meta.gguf
├── model-00000.mmbw
└── model.verified.json       # when a seal is created
```

### What each file does

- `model.mmb-meta.gguf` — model metadata and tensor directory without the original tensor payload.
- `model.mmb-map.json` — physical block map: shard, offset, length, hash, layer and expert.
- `model.mmb-layout.json` — MoE topology and expert segment layout.
- `model-00000.mmbw` — raw GGML-encoded core and expert bytes.
- `gate.json` — runtime configuration for cache, integrity and server settings.

MMB does not dequantize and requantize weights during conversion. The encoded GGML slices are preserved.

Format details: [`docs/model-format.md`](docs/model-format.md)

# Quick start — Windows

The repository includes both user-facing tools and development sources.

For the current source distribution, the native backend must be compiled once on the machine.

## Requirements

- Windows x64
- Python 3.11+
- CMake 3.20+
- Visual Studio / Build Tools with MSVC C++ x64/x86

The Python runtime itself has **no third-party runtime dependencies** beyond the Python standard library.

### 1. Open MiniMaxBrain

Run:

```text
starter.bat
```

For an already converted bundle, the normal flow is:

```text
[1] Build/test native backend
[3] Prepare existing MMBW bundle
[6] Direct MMB chat
```

Or use:

```text
[7] Direct MMB Web/API
```

### MSVC environment

If `cl.exe` and `nmake.exe` are not visible, run MiniMaxBrain from a Visual Studio **Developer Command Prompt** or activate the x64 environment with the appropriate `VsDevCmd.bat -arch=x64` for your Visual Studio installation.

## Build manually

Install the local Python package:

```bat
python -m pip install -e .
```

Build the backend:

```bat
python tools\build_native.py
```

A Windows Release build normally produces:

```text
native\build\Release\mmb_backend.dll
```

The build also runs the native MMB and GGML tests.

# Convert a GGUF MoE model

Using the conversion wizard:

```text
conversor.bat
```

Or directly:

```bat
python mmb.py convert ^
  --gguf "modelos\model.gguf" ^
  --output "modelos\model-mmbw" ^
  --cache-gib 1
```

The source GGUF is currently kept intact during conversion, so make sure the disk has enough space for both the source model and the generated MMB bundle.

---

# Use an existing MMB bundle

If the bundle already exists, **do not reconvert it**.

Create the runtime config if needed:

```bat
python mmb.py prepare ^
  --bundle "modelos\model-mmbw" ^
  --cache-gib 1
```

`prepare` does not rewrite the `.mmbw` payload.

---

# Terminal chat

```bat
python mmb.py chat ^
  --bundle "modelos\model-mmbw" ^
  --cache-gib 1 ^
  --ctx 2048 ^
  --tokens 128
```

Or:

```bat
python mmb.py chat ^
  --config "modelos\model-mmbw\gate.json" ^
  --ctx 2048 ^
  --tokens 128
```

After conversion, the original GGUF is not used as the runtime backing for routed experts.

# Correctness model

MMB is designed to fail closed.

Important invariants:

1. The neural router determines the expert IDs.
2. MMB does not invent or replace routing decisions.
3. Routed expert bytes come from `.mmbw`.
4. Expert memory remains leased while a GGML kernel uses it.
5. Leased blocks cannot be evicted.
6. Shape, type and encoded length must match the tensor contract.
7. Integrity failures abort the operation when validation is enabled.
8. The paged-kernel metric is recorded only after successful compute.
9. There is no silent fallback to GGUF, `llama-server` or synthetic text generation.

# Performance milestone: make paging disappear from the critical path

MMB already proves that bounded expert residency works. The next engineering milestone is performance.

The target is **not** simply “make the pager faster”.

The target is:

> **Make CPU and memory bandwidth the primary generation bottlenecks, rather than the MMB pager.**

The current optimization plan is incremental:

```text
A1 — persistent shard I/O
      ↓
A2 — batched parallel Top-K misses
      ↓
A3 — segmented hot/cold expert cache, only if real traces justify it
      ↓
async overlap / prefetch where router dependencies permit it
      ↓
compute-bound runtime
```

These optimizations are being validated independently before they are promoted into the native production pager.

### Compute-bound success criteria

The planned measurements include:

```text
paging_tax = pager_wait / decode_total

target: <= 10%
ideal:  <= 5%
```

and comparison against a hot-cache / compute ceiling on the same hardware.

The goal is that once MMB is optimized, changing CPU or memory speed should matter much more than changing the pager implementation.

See the implementation design in the project performance specification / technical documentation.

# Long-term direction

The architecture is intended to explore model capacities much larger than the RAM available for routed experts.

The roadmap is roughly:

```text
real MoE correctness
        ↓
bounded expert working set
        ↓
compute-bound pager
        ↓
long-run stability
        ↓
multi-shard / resumable conversion
        ↓
larger-than-RAM expert banks
        ↓
100+ GiB models
        ↓
TB-class MoE experimentation
```

A TB-class model is a **research target**, not a currently validated capability.

At that scale, new problems become dominant:

- shard layout;
- filesystem behavior;
- conversion time;
- resumable conversion;
- source-space reclaim;
- core-model residency;
- I/O scheduling;
- long-run cache behavior.

# Current limitations

- The validated real-model path is CPU-based.
- GPU/VRAM expert paging is not yet validated.
- The GGML provider is currently process-global, so only one `MMBLlamaRuntime` should be active per process.
- The current converter keeps the source GGUF while creating the MMB bundle.
- The core model is still resident; MMB 0.3 specifically proves paging of routed expert weights.
- Performance work is ongoing; experimental pager benchmarks are not equivalent to end-to-end generation throughput until integrated into the native runtime.
